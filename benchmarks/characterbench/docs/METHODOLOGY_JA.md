# 計測仕様 — KCB v0.1

## 単位と集計

`unit` は単発設問または対話台本。各unitはキャラID・family・mode・turnsを持つ。`response` は候補モデルの1回の生成。`target` は自然文の採点単位で、単発応答1個または成功した対話全体。`repeat` は同じ設問を新しい会話状態で繰り返す試行で、best-of-kではない。

全データ1反復: 132 units、264 responses、84 natural targets。12キャラ×(4診断＋6単発＋12対話応答)。3反復では792 responses、252 natural targets。

## 状態診断

`json_exact` はJSONオブジェクトであること、重複キーなし、非有限数なし、過不足のないキーと値、正確な型を検査する。キー順は問わない。booleanとinteger、integerとfloat、JSON nullと文字列"null"は別。Unicode文字列の勝手な正規化もしない。

厳密判定でコードフェンスや前置きがあれば失敗する。外側のJSONフェンスだけを許すloose値も別フィールドへ出すが、厳密値を上書きしない。状態の正答と指示遵守が混ざる診断であることを認め、自然会話の能力点として解釈しない。

各キャラc・系統f・反復rの正誤をx(c,f,r)とする。まず反復の平均、次にそのキャラの系統平均、最後にキャラの平均を取る。

```
cell(c,f) = mean_r x(c,f,r)
character(c) = mean_f cell(c,f)
diagnostic_macro = mean_c character(c)
```

HTTPエラーや依存スキップが記録された診断は0。成功応答のみの条件付き正答率も別記録。中断等で未記録の課題は暗黙の0にせず、網羅率とともに暫定値を示す。

誤答解析用には `diagnostic_fields` でキーごとの正答率も示す。厳密JSONかつキー集合が完全一致した応答だけで、各値を型込みで判定する。形式違反の応答は全フィールドを不正答とする。主指標の全キー完全正答を置き換えたり、個別フィールドをキャラ品質の点数として合成したりはしない。

## 自然文の表面仕様

空でない、指定の最大Unicode文字数以内、Markdown見出し等がない、明示的に要求した文字列が含まれる、といった検査。`contains` は完全に表面的な包含検査であり、「その単語を自分の好物だと言った」と判定するものではない。

自然文は各応答を単位として表面適合を評価するため、12ターン対話はそのキャラの単発より多くの観測を占める。この値は会話出力のフォーマット遵守率であり、全般品質スコアとして異なるmodeを混ぜない。意味のrubricでは対話全体を1単位に戻す。

箇条書き禁止の字面チェックはMarkdownの `-` 等に加え、行頭の「・」「●」等も検出する。これを見落としていたv0.1.1以前の表面適合率と、v0.1.2以降の値を同じ採点規則の結果として比較しない。保存済み応答は `regrade` を明示的に実行した場合だけ再採点し、旧評価をローカルに退避する。生成時の版と採点時の版を別記する。

## Rubric judge

8軸: preference / persona / agency / style / robustness / emotion / japanese / continuity。全課題に全軸を無理に当てず、設問が露出する軸だけ採点する。整数1〜5、判断不能null。引用evidenceと短いreasonが必要。引用がcandidate_text中に実在することを検査する。

同一target・dimensionで複数judgeの非null点があれば平均し、キャラごとに平均し、キャラ間を等重みで集計する。無効JSON、根拠が見つからない、欠落dimensionは採点エラー。nullとエラーを0点へ代入しない。複数judgeは独立性を保証しない。

レポートは予定targets→完了して採点可能なtargets→有効採点があるtargetsと、dimension別の採点数／採点可能数を示す。未完了対話やエラーが意味評価から落ちるため、成功率と合わせて読む。応答スナップショットhashの違う古いjudge結果は無視する。

## A/B比較

同じ固定ユーザー台本に対する単発応答または**対話全体**を比較する。Aで生成された前ターンとBで生成された前ターンが異なるのに、後の一文を「同じ入力の単発」として比較しない。

順序1をA/B、順序2をB/Aとして実行し、順序2の候補名を元へ戻す。両者が一致すればstable、一致しなければorder_sensitive。後者をtieにしない。通信・構造エラーも別status。

stableでA勝ち=1、B勝ち=0、tie=0.5、both_bad=0.5という対称的選好値を集計する。ただしboth_badの件数を別に表示する。両者とも悪い回答ばかりでも選好値が0.5になるため、単独の品質点には使えない。stableに限定した選好は条件付きで、安定率・未解決数・失敗数が必要。提示左側が選ばれた割合も探索的に出す。長さ補正回帰は実装していない。

## 人間評価

モデル対応表を別に保持し、HTMLへは候補名A/Bのみ渡す。どちらを好むかを匿名で記録し、同一課題・同一匿名IDは一票。矛盾する重複は自動的に最新へ置換しない。skipを選好の分母から除外する。課題ごとに人の値を平均→キャラごとに平均→キャラ平均を計算する。

同じ画面を複数人に渡すと、その画面における左右順序は同じである。課題間ではランダム化済みだが、評価者ごとの左右カウンターバランスはv0.1では未実装。匿名IDだけなので複数IDの同一人物検出もしない。観測は便宜サンプルであり人口代表性はない。

`calibrate` は同じrunスナップショットかつstableな自動judgeと重なる人間票でカテゴリーの完全一致を出す。未解決例を除くため選択バイアスが残る。これは校正用の観測値であり、judgeが妥当だという証明ではない。評価者を別の独立clusterとして再標本化する多階層推定は未実装。

## 区間推定

`cluster_estimate` はキャラごとに平均した値を2,000回、復元抽出してpercentile 95%区間を出す。独立な標本数が264や792あると見なさず、12キャラのclusterを使う。1clusterでは区間はnull。

状態診断のA−Bは同じキャラ・family・反復の対応差を使い、キャラ単位で再標本化する。別途、family単位の探索的感度分析も出す。これはtwo-way bootstrapではない。12キャラ／4診断familyの共有構造、小標本、公開固定テンプレートの偏りを区間だけで解消できない。

区間が0をまたぐなら「差が確定しない」。同等性試験をしていないので「同じ性能」とは言わない。全問正解で区間が一点になっても一般化の不確実性が消えたわけではない。多重比較の補正やIRTでの項目校正は未実装。

## 速度・原価

生成がtoken上限で切れた場合、部分本文を保存しつつ `truncated` として採点対象から外す。OpenAI互換サーバーが正常終了の `stop` 以外（`length` / `max_tokens` を除く）を返した場合も本文を保存するが、`error` として非採点にする。対話中なら後続ターンは `skipped_dependency`。旧v0.1のrunでは切断応答が `ok` と記録されている場合があるため、異なる実装版のスコアを無条件に比較しない。自然文の表面仕様は単発と対話の内訳も表示し、対話ターン数による重みを確認できるようにする。

`require_no_reasoning` はサーバーから観測できるreasoningフィールド・usage・可視タグを検査する。設定の完全な遵守やモデル内部で一切思考しないことの証明ではない。候補モデル自身によるrubric採点は自己評価として別表示し、独立した品質証拠としない。

TTFTはリクエスト送信開始から最初の**表示用本文**を受信するまで。role-onlyイベントや別フィールドのreasoningイベントで開始しない。非ストリーミング、System参考bridgeでは正確なTTFTを計れないのでnull。単なる総待ち時間をTTFTと偽らない。

latencyはクライアント観測の呼び出し完了までで、ネットワーク、待ち行列、prefill、生成を含む。Systemでキャッシュ応答の再配信と明示されたものは生成latency集計から除く。p50/p95は成功応答を対象にし、失敗率も別表示する。warmupは別ファイルへ保存し集計しない。

明示的な `--retry-errors` は再試行前の失敗・依存スキップを `retry_attempts.jsonl` に退避する。成功済みの応答は選び直さない。`--retry-workers` で再試行だけ並列数を変えた場合はmanifestとsummaryに記録し、成功応答のlatency分布は異なる同時実行条件の混合であると警告する。退避した失敗を消して「初回から成功した」とは主張しない。

usageはサーバーが返したtoken値のみ。文字数、SSEのchunk数、Pythonのsplit結果をtoken数としない。v0.1は純decode tok/s、GPU utilization、同時接続のSLA、KVキャッシュ量、GPU秒単価を実測しない。

設定に入力／出力100万token当たりのUSD単価を与え、全成功応答に必要usageがある場合のみ、設定値ベースの概算を出す。これはキャッシュ割引、reasoning課金体系、未成功呼び出し、税、warmup、GPU常時費、採点者の費用を含まない。`known_usage_cost_subtotal_usd` は部分的な既知分の小計で、実請求額ではない。

## 再現性とデータ流出

dataset＋protocol＋設定＋選択units＋repeat＋seed＋workers＋warmupをfingerprintへ含める。resumeは一致が必要。ただしAPIモデルが同じIDで更新されたり、GPU kernelが非決定的だったりする可能性は残る。重みhash・backend版は利用者がmetadataに記録する。

Coreの候補モデルには公開カードと可視履歴のみ。eval/gold/notesは渡さない。judgeには採点用メモを渡す。候補にとっては非公開だが、ZIP利用者に対しては公開データであり、学習汚染がないとは主張できない。
