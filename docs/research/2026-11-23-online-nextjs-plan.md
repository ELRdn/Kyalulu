# Kyalulu オンライン版の Next.js 移行計画

2026-11-23。対象は app.kyalulu.com のオンライン版全体。main の 4f24140 と作業ツリーをもとにした実装前の提案。

## 到達点

公開ページ、アカウント、会話、制作、研究・管理を含め、オンライン版の画面と URL を Next.js App Router で管理する。ブラウザで使う端末内推論、遠隔 PC 接続、インストール済み PWA の更新も移行範囲に含める。個人データは選択した実行先に置く。Electron・PC 配布物は共通 UI の利用者として互換性を保つ。独立した公式サイト・ガイドは別の配布単位とする。

| 担当 | 完成形 |
|---|---|
| Next.js | オンライン画面、公開 HTML、URL・レイアウト・読み込み・エラー表示。公式キャラの初期表示はそのキャラに必要な公開データだけで構成する |
| ブラウザ | 入力・下書き、生成状態の復旧、実行先選択、端末内データ、Worker、遠隔 PC との暗号化接続。サーバーから読めないデータで初期 HTML を作らない |
| Python / Relay | FastAPI の既存 API、認証コールバック、履歴・記憶・生成・見積もり・精算・同期・公開判定。Relay は暗号化通信を中継する |
| 配信 | 同じオリジンでページは Next.js、既存 API は Python へ振り分ける。Worker・WASM・オフライン起動用 HTML はバージョンを対応させて配る |

## 各段階

| 段階 | 実装単位 | 次へ進む条件 |
|---|---|---|
| 0　現状を固定する | 画面・公開可否・実行先・必要な権限・直リンク・担当サービスを一覧化。旧ハッシュ URL、ログイン、ペアリング、旧 Mobile の移行用文書、404、静的ファイルも記録。公開版・ステージングで同じ代表導線を記録する | 稼働版・プロキシ経路を確認し、現状の直接 GET 404 と手元のルート定義の差を説明できる。比較用の端末・回線・データ・操作・計測結果がそろう |
| 1　並行稼働の土台 | モノレポに apps/online（仮称）。現行 React の表示部品と型を必要な分だけ再利用。まずステージングで Next と既存 Web を同一オリジンに置き、ページ群単位で切り替える。新旧間は通常のリンク、Next が所有する範囲内は App Router で遷移 | 1ルートを新旧に往復できる。認証 Cookie、OS の戻る操作、404、既存アセット、配信ヘッダーが期待通り。CSP の下で本番ビルドが起動する。旧 SW が新ページを古い HTML に置換しない。VPS の実測メモリに余裕がある |
| 2　最初の利用体験を通す | 一般向け公式キャラの詳細 → ログイン → 入力済みの最初の一言を引き継ぐ → 会話の開始。キャラ単体の公開読み取りを用意し、個人の履歴・設定は後から取得。チャット本体はこの段階では既存画面へ渡せる | 新規訪問の HTML に対象キャラの紹介と OGP がある。未ログイン→ログイン・戻る・再読込でキャラと入力が維持され、会話開始・初回送信は一度だけ。公開紹介にセッション一覧取得が不要。基準値と比較してから対象を広げる |
| 3　Cloud の会話を移す | /chats と /chats/:sessionId。既存の送信・見積もり・SSE・生成 ID・下書き復旧をクライアントから使う。Next を介した生成の再実装は不要。履歴表示、取消、再生成、分岐、削除を含めて切り替える | 切断・再読込・二重操作・アカウント切替後も保存済み履歴と表示が一致し、二重生成・二重課金がない。見積同意と取消が機能。旧 UI に戻しても生成結果を確認できる |
| 4　オンラインの日常・制作画面を移す | ホーム・発見・公開作品・作者 → プロフィール・設定・法務 → 作成・投稿・審査 → Studio・研究・診断の順に小さく切り替える。Cloud や遠隔から使えない管理機能は権限どおり表示。検索条件・ページタイトル・戻る操作も移行する | ルート表の既存機能が埋まり、匿名・所有者・別アカウント・制限付き閲覧・管理権限の代表ケースが通る。非公開化した作品の本文や OGP が公開キャッシュに残らない |
| 5　端末内・遠隔 PC・PWA を仕上げる | Next の画面群を各実行先の既存 transport につなぐ。端末用には事前取得できる固定のクライアントシェルを用意し、任意の会話 ID は端末で解決。Worker/WASM の integrity とヘッダー、Remote の fragment 処理、移行用文書、旧 PWA からの更新を通す | インストール済みの旧版から更新後、オフラインで既存会話を開き生成・保存・再起動できる。未送信同期・下書き・モデルを維持。遠隔 PC のペアリング・切断・復帰で誤送信がない。実機結果をエミュレーションと区別する |
| 6　主配信を切り替え、旧オンライン UI を終了 | ステージング → 限定利用 → 一般公開。ルート群と利用者の割当を安定させ、進行中の会話の途中で UI を切り替えない。旧バージョンのアセットを更新期間中は配信する | 全オンライン画面が Next で開き、旧 UI への通常転送がゼロ。観測期間中に主要導線・エラー率が合格し、復旧手順を実演済み。旧オンライン配信と重複する URL 定義を撤去し、PC 配布が依存するコードは残す |

端末・PWA の本移行は段階 5 だが、成立性は段階 1 で試す。既知・未知の会話 ID、旧 SW 制御下の再訪、ネットワーク遮断後の再起動を小さいシェルで確かめる。ここで失敗した場合は端末用の出力・起動方法を決め直してから画面移植を広げる。

## 配信と復旧で先に決めること

- Caddy の既存例は全リクエストを Python に渡す。並行稼働時は Next のページと /_next/、既存の /api/・/auth/callback・/source.tar.gz、旧資産の担当を明示する。/device/ と /migration/ は専用文書・専用ヘッダーがある。旧ハッシュはブラウザで変換し、ペアリング用 fragment を先に消費する。
- 公開ページの HTML とアカウント依存の読み取りを分ける。既定の noindex は公開方針を決めた一般ページだけ変更する。制限付き作品や個人履歴は共有キャッシュの対象外。公開取り下げ時に HTML・メタデータを失効させる。
- 同じオリジン、Cookie、IndexedDB・OPFS、生成 ID と復旧記録を継承する。移行期間中の永続形式変更は新旧どちらでも読み取れる順番で行う。Next の処理から同じ生成を再送しない。
- 障害時は対象ルートの配信を旧 UI に戻す。開いたままのページと古い SW には既存資産を配り続ける。配信先変更だけでインストール済み PWA は巻き戻らないため、互換 SW の更新経路も別に検証する。重複課金、利用者をまたぐ表示、履歴消失は即時停止条件。

## 改善をどう判定するか

開発前に同じ端末・回線・会話データで現行値を取る。小規模の間はラボ計測の反復数と生値を記録し、十分な利用数がある段階で実ユーザーの p75 と分母を出す。

| 観点 | 判定方法 |
|---|---|
| 初期表示 | キャラ名・本文が初期 HTML にあるか。低速モバイルのコールド訪問で LCP、紹介を読めるまでの時間、初期 JS、API 要求数を比較する |
| 会話開始 | 直リンクから入力可能になるまでの時間、ログイン復帰成功率、下書き喪失・重複送信件数。ユーザーの操作待ちは通信・描画時間と分ける |
| 会話中 | 同じモデル・履歴条件で既存の context_fetch_ms、quote_fetch_ms、post_to_first_body_ms、post_to_full_ms を比較。推論そのものと画面移行の効果を混同しない |
| 開発のしやすさ | 「一般向け詳細画面を1つ追加する」変更例で、新旧それぞれの URL 定義箇所、重複する取得・描画処理、レビューから動作確認までの手順を記録する。認可判定は引き続きサーバーで検証する |

## 最初の実装チケット

1. **現行値と URL 表**。App.tsx・cloudGuest.ts・WebDist・実配信を突き合わせる。公式キャラ1人で「直接訪問→ログイン→初回会話」の現行結果を保存する。
2. **並行配信と復旧の実証**。ステージングの同じ URL を旧・新へ振り分け、Cookie、CSP、旧 SW、専用シェル、API とアセット、ロールバックを確認する。ここでビルド方式と運用コストを決める。
3. **公式キャラ1人の導線**。Next の詳細画面を既存認証・既存チャットにつなぐ。個人履歴を待たない初期表示とログイン後の入力復帰を実証し、数値と差分でレビューする。
