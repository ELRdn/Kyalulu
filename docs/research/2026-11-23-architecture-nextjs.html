起動・配布の違い

Vite は Web の HTML・JS・CSS をビルドする。統合版では Worker、WASM、オフライン用の配布ファイル一覧も作る。通常の Web はパスで、Electron と /device/ はハッシュで画面を切り替える。旧 Mobile は別のエントリを持つ。Electron は共通の Web エントリを読み、製品版の app://kyalulu からローカル API を転送する。npm ランチャーはネイティブ版 Web を含むローカル Runtime をループバックで起動する。

統合 Cloud の配布構成例は、Caddy → Uvicorn の FastAPI。ビルド済み Web と Python をコンテナに同梱する。LP と日英のガイドは別の静的サイトで、ガイド生成時にサイトマップや検索用データも作る。

データと同期の境界

Cloud は Supabase Auth で認証し、Python がセッションから利用者を決める。運営用 control.db はアカウント・課金などを、tenants/<owner>/data.db は利用者ごとの会話などを扱う。ブラウザでは表示設定や未確定の送信情報に localStorage も使う。Service Worker のキャッシュはビルド時に指定したシェルと資産用で、会話履歴はそこに入らない。

端末での生成とアカウント同期は別々の操作。同期の許可と対象データの保存方針を確認し、変更を outbox に記録して要求 ID と改訂番号を付ける。競合・削除・再開を扱うため、単純なクラウド上書きとは異なる動作になる。

Cloud で「送信」を押したあと

公式キャラページから会話を作る場合

  1. 送信元の確認Cloudのアカウントと配信対象を確かめる。
  2. 会話の保存FastAPIが設定と挨拶を保存し、履歴の版を返す。
  3. チャットを開くApp Routerが遷移。アカウント確認を経て履歴を読む。
  4. 最初のメッセージ保存した下書きと履歴の版を使い、見積もりと生成に進む。

会話でメッセージを送るたびに

  1. ① 送信準備生成 ID を確保。保存済み履歴を使う場合は版を確認。
  2. ② 見積もり経路と上限額を取得。追加同意が必要なら画面で確認。
  3. ③ 生成予約してキューへ。設定、状態、記憶、履歴から入力を作り、モデルを呼ぶ。
  4. ④ 検証・保存本文と状態更新を検証し、成功したターンを保存。料金を精算。
  5. ⑤ 表示SSE で進捗を通知し、成功時の done で確定本文を表示。

③〜④の進捗通知は生成中に届く。モデルが最初のトークンを返した時刻と、ユーザーが最初の本文を見る時刻は違う。PC の Python 経路は暫定本文と再試行時のリセットを返せる。現行の統合 Device は Worker の差分を内部で集め、進捗を返し、解析・保存後に本文を確定する。

チャットを速くしたい場合に見る計測値

クライアントは履歴照会、見積もり取得、同意待ち、送信後の初本文・完了を個別に記録する。Cloud 側にはキュー、生成、保存の所要時間もある。同意操作の待ち時間を分け、同じモデル・会話条件で調べると改善箇所を選べる。実行中に接続が切れた場合は、保存した生成 ID で状態と履歴を照合する。

公開ページで起きていること

手元の Cloud は /discover と対象の公式一般向け /characters/:id に、本文・タイトル・canonical・OGP を含む HTML を返す実装。起動後に React が本文を描き直す。作品・作者ページは React の画面と API を持つが、この Python の HTML 生成対象には含まれない。

Next.js の採否を決める条件

選択肢得られるもの判断
Vite ＋ FastAPI を継続共通画面、オフライン、デスクトップの配布を維持。少数の公開ページは既存の Python HTML 生成を拡張できる。画面の取得処理やルート定義の整理を少ない変更で進める対案。
公開面に Next.js を追加作品ごとのメタデータ、サーバーレンダリング、静的生成や再検証を React 側でまとめられる。一般公開の作品が増え、検索・SNS経由の流入が重要になる場合の候補。
オンライン版全体の画面を Next.js に移行一覧から個別ページ・ログイン・チャットまで同じルーターで管理できる。公開データはサーバー、会話入力・生成の復旧・端末 API はクライアントで扱う。今後の開発の主軸に推奨。送信後のUXと実機・配信先の確認を本番切り替えの条件にする。
全配布版・Python Runtime まで書き換え言語やフレームワークをそろえても、SQLite・推論・課金・暗号化中継・オフライン配布の動作は引き続き実装・運用する。一括移行は推奨しない。端末版のシェル共通化はオフライン起動と任意の会話 ID の復元を実証して判断する。

共通のキャラ詳細画面ではキャラ一覧・世界一覧・セッション一覧をまとめて取得する。Next.js の公式キャラ個別ルートでは公開紹介に必要な1件を先に描画し、個人設定や履歴は後から読み込む。作品と作者の個別ページにも、初期本文と共有メタデータで同じ取得結果を使う構成を導入した。作品・作者ページの共通処理 · カタログ取得

公開面を試すなら、まず一般向けの公式キャラ詳細を1種類選ぶ。直接アクセス・JS 実行前の本文・SNS プレビュー・会話開始までの導線を比較する。ユーザー投稿に広げる段階で、公開取り下げ時のキャッシュ無効化と、ログイン状態で表示が変わるデータの扱いも確認する。

静的エクスポートを使えば Next.js の常駐サーバーは不要。ただしリクエストごとの描画や ISR（公開後の段階的な再生成）は使えず、動的な ID はビルド時に列挙する必要がある。これらが必要ならサーバー実行環境とキャッシュ更新の運用が増える。
