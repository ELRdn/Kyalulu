# Incremental sync byte serialization

2026-10-26. Application source `7e44841`. Fictional accounts, conversations,
disposable SQLite/IndexedDB and local browser fixtures only. No production data,
funds, provider credentials, deployment or merge was changed.

## Change and compatibility

Browser sync hands its durable batch object directly to the uploader. It no
longer stringifies the entire batch, UTF-8 encodes that whole string, parses it
again to recover its request ID, or allocates another whole-batch byte buffer.
Plain JSON is serialized incrementally into the existing 1MiB transfer pages.
String slices use platform JSON escaping and retain surrogate pairs at slice
boundaries; key order, omitted object values, array nulls and primitive formatting
retain the prior `JSON.stringify` bytes. Cycles and unsupported non-JSON objects
fail before any network request, leaving the persistent outbox available.

Native upload and Cloud download use standard-library JSON iteration and bounded
UTF-8 buffers. Native batch admission also stops counting at its existing batch
threshold, avoiding a whole encoded copy merely to choose a batch. The compact
wire bytes are unchanged; already staged manifests keep their request IDs, total
size, hash, part boundaries, restart position and receipt validation. Ordinary
small bodies still use the existing inline endpoint; pre-upgrade inline receipts
still use the original content-validation path.

The first pass computes size/hash and the second produces parts. This trades
another serialization pass for less temporary memory. Browser consent checks
yield through existing IndexedDB operations; Native hashing yields to its event
loop. Current account/consent/outbox guards run before sending, including after
hashing small inline requests. Cancellation retains unsent local data. Encrypted
Cloud page storage, owner/revision/deletion checks and atomic commit remain in use;
no plaintext staging file or new dependency is introduced.

## Required work still open

This removes transfer serialization copies, not whole-entity materialization.
Browser entity/outbox IndexedDB records, `getAll`, historical/library clones,
Native captures/outboxes and canonical hashes, Cloud encrypted entity writes and
`EntityTransfers.commit`, and Browser/Native download parsing still materialize
whole objects or JSON. Python's standard JSON iterator also retains one encoded
scalar before UTF-8 chunking; a huge individual string is not covered by the
many-record allocation test. Further segmented storage/projection and bounded
receive are required before accepting **250MB/1GB single conversations**.

Real plan-capacity workloads, old-snapshot recovery at that scale, process RSS,
physical phones, interrupted real-model migration and production rollout remain
unqualified. Existing distribution candidate `0d9b2f5` predates these changes;
final distributions must be regenerated and audited from the completed source.
