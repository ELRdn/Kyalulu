# 実装計画・到達点

## v0.1で実装したもの

| 領域 | 実装 | 確認方法 |
|---|---|---|
| 出題設計 | 12キャラ、120単発、12×12ターン、Core/Systemの分離 | データ件数・構造テスト |
| 状態判定 | 所在／所持、観測者の認識、日時、明示フィールド | 公開イベントからgold再計算 |
| 接続 | OpenAI互換HTTP/SSE、モデル列挙、明示設定、System session contract | localhostプロトコルシミュレーター |
| 保存と再開 | SQLite応答単位保存、hash一致resume、明示的retry | 失敗・中断・変更拒否テスト |
| 主観評価 | rubric、証拠引用検証、複数judge、A/B順序反転 | MOCKとHTTPテスト |
| 人間評価 | モデル名分離HTML、匿名票、JSON保存／import、重複検証 | ブラウザ操作＋単体テスト |
| 比較 | 対応する状態診断差、キャラcluster区間、順序未解決の可視化 | 合成データでの集計テスト |
| 配布 | Python標準ライブラリのみ、Windowsランチャー、説明書、オフラインレポート | 展開後のクリーン実行 |

詳細な実行結果は `ACCEPTANCE_TESTS.md` に記録する。実装テストが通ることと、ベンチの科学的妥当性は別である。

## 次の計画（未実施）

### Phase 1 — 実機の接続確認

使うサーバーと実際のモデルIDを固定し、22応答のsmokeを実行する。テンプレート、JSON途中切れ、thinkタグ漏れ、量子化、usage対応を確認する。ここでは品質順位を決めない。

### Phase 2 — 同条件の候補比較

複数の異なるモデル系列をall・複数反復で測る。主条件は先に固定する。thinking/MTP/量子化等の設定差は別runにし、計測値と失敗例を監査する。実験に必要なモデル利用条件や費用は利用者側で確認する。

### Phase 3 — 人間ラベル

複数の日本語評価者からブラインド比較を集める。狭い好み、疲労、左右偏りを調べる。judgeと不一致の例を人間が読み、口調だけ、長さだけ、優しさだけの採点になっていないか分類する。数値だけで正しいjudgeを選ばない。

### Phase 4 — データの修正と独立検証

gold不備や曖昧課題を開発セットで修正。新しい独立シナリオ・キャラを作成し、評価前に版を固定する。公開セットでモデルを微調整したら独立テストを用意する。

### Phase 5 — Kyalulu本体との統合

実際のMemory/RAG/Stateのresetと隔離を備えるadapterを実装する。複数セッション・日をまたぐ記憶、取り消しと削除、訂正、出所帰属、キャラ間漏えいを別System suiteで測る。既存Kyaluluのコードは今回変更していない。

### Phase 6 — 推論原価と本番運用

対象GPUで同時数・入力長・KV cache・queue・TTFT・失敗率を測る。比較するのは単発tok/sだけでなく、条件を満たす完了対話あたり原価。v0.1の設定単価概算をそのままGPUクラウドの損益分岐へ使わない。

## 今回、実施していないこと

実際のGemma／Spotwrite／その他LLMによる生成、第三者による人間ラベル、judgeの日本語妥当性検証、独立private/live set、IRT、長さ補正回帰、Eloランキング、実GPU throughput、Windows実機の起動、Kyalulu既存repoへのpush・deploy。これらが完了したと報告しない。
